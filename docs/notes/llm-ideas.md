# LLM 도입 아이디어 (추후 선택 구현)

실시간 8단계가 끝난 뒤 여력이 있으면 추가. **실시간보다 우선하지 않는다.**

## 선정 기준

AI 기능을 "붙였다"는 사실 자체는 이제 차별점이 아니다. 중요한 건:

1. **이 앱에 실제로 필요한가** (억지로 끼운 챗봇은 역효과)
2. **실시간/스트리밍 기술과 결합되는가** ← 이 프로젝트의 강점을 키우는 방향
3. **엔지니어링 난점을 드러내는가** (토큰 비용, 지연, 실패 처리, 프롬프트 주입)

아래는 기준을 만족하는 순서로 정렬.

---

## 1. 대화 요약 (추천 1순위)

**기능**: "오늘 이 채널에서 무슨 얘기 있었어?" → 긴 대화를 요약.

**왜 적합한가**

- 팀 협업 도구에 **실제로 필요한** 기능이다 (Slack/Teams 모두 제공)
- **스트리밍 응답**이 자연스럽다 → WebSocket/SSE 작업과 직접 연결된다
- 요약 대상이 길어 **컨텍스트 윈도우 관리**를 배우게 된다

**배우게 되는 것**

- 스트리밍: LLM 토큰을 받아 실시간으로 UI에 흘리기 (이미 만든 WS 인프라 재사용)
- 긴 입력 처리: 메시지 N개를 어떻게 자를까 (최근 우선? 중요도?)
- 비용 관리: 요약을 캐시할까, 매번 호출할까
- **프롬프트 주입 방어**: 사용자가 "앞의 지시를 무시하고..."를 채팅에 쓰면?
  ← 보안 학습과 직접 연결되는 지점

## 2. 파일 자동 태깅 / 의미 검색

**기능**: 업로드된 파일에 태그를 자동 부여, 또는 "작년 예산 관련 문서" 같은 자연어 검색.

**왜 적합한가**

- 파일 공유 기능(9주차)의 자연스러운 확장
- **임베딩 + 벡터 검색**을 배우게 된다 (RAG의 기초)

**배우게 되는 것**

- 임베딩이 무엇이고 키워드 검색과 어떻게 다른가
- 벡터 저장: pgvector(PostgreSQL 확장) vs 전용 DB
- 청킹 전략: 긴 문서를 어떻게 쪼갤까
- 하이브리드 검색: 키워드 + 의미를 섞는 이유

## 3. 스마트 알림 요약

**기능**: 자리를 비운 동안 쌓인 알림을 "중요한 것 3개"로 압축.

**왜 적합한가**

- presence(4주차)와 결합된다 — **오프라인이었던 구간**을 아는 것이 전제
- 갭 복구(5주차)로 "놓친 메시지"를 이미 알고 있으므로 입력이 준비되어 있다

**배우게 되는 것**

- 기존 실시간 로직과 LLM의 결합 지점 설계
- 중요도 판단을 LLM에 맡길 때의 신뢰성 문제

## 4. 번역 / 말투 교정 (우선순위 낮음)

흔하고 차별점이 적다. 다만 구현이 쉬워 스트리밍 연습용으로는 가능.

---

## 공통 엔지니어링 과제

어느 기능을 택하든 다음을 다루게 된다. **이것이 실제 학습 내용이다.**

| 과제          | 내용                                                        |
| ------------- | ----------------------------------------------------------- |
| 스트리밍      | 토큰 단위 응답을 UI로 흘리기. 중간에 끊기면?                |
| 비용          | 호출당 토큰 비용. 캐싱·요약 주기 설계                       |
| 지연          | LLM은 느리다(수 초). 낙관적 UI·로딩 상태 설계               |
| 실패 처리     | API 장애·레이트리밋 시 UX                                   |
| 프롬프트 주입 | 사용자 입력이 프롬프트에 들어가는 구조의 위험               |
| 키 관리       | API 키를 **절대 클라이언트에 두지 않는다** → 서버 경유 필수 |

**키 관리는 보안 학습과 직접 연결된다.** LLM 기능을 붙이면
"API 키를 어디 두는가"가 실제 문제가 되므로 `.server/` 경계를 쓰는 실전 사례가 된다.

## 구현 시 결정할 것

- 모델: Claude(Anthropic) / OpenAI / 로컬(Ollama)
- 호출 위치: React Router `action` (서버) — 클라이언트 직접 호출은 키 노출이므로 불가
- 스트리밍 전송: 기존 WebSocket 재사용 vs SSE 별도
